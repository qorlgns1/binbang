> **지금 유저가 0인 건 아이템이 틀려서가 아니라 유통을 한 번도 안 했기 때문이다.**

## 1. 현황 진단

### 제품 포트폴리오 결정
- **빈방(`apps/web`)에 올인.** 통증이 진짜고(취소표), 청중이 도달 가능하고(카페), 수익 경로가 동작함(Agoda 제휴).
- **여행 AI(`apps/travel`)는 강등.** mindtrip/ChatGPT/구글과 1인이 채팅 품질로 경쟁 불가. 죽이지 말고 **빈방으로 유입시키는 SEO 깔때기**로만 유지 (투자 X, 자산으로만 활용).

### 핵심 문제 (병목 4개)
1. **유통(distribution) = 0.** 인프라는 시리즈A급인데 존재를 아무도 모름. 청중이 아니라 인프라를 빌드한 결과.
2. **다시 올 이유 없음 (retention).** 창업자 본인조차 재방문 동기 없음 → 마케팅 문제가 아니라 제품 구조 문제.
3. **에피소드성 사용.** 여행 끝나면 이탈 → "사이트 MAU"는 알림 도구의 본성과 충돌.
4. **로그인 강제 = 신뢰 장벽.** 처음 보는 인디 사이트에 OAuth를 *가치 경험 전에* 요구 → 대부분 이탈.

### 피벗 충동에 대한 판정
- 피벗하고 싶은 진짜 이유 = **"막혀서 / 확신이 없다".** → 이건 피벗 신호가 아니라 **증거 부족 신호**.
- 닫힌 빌드 루프(외부 신호 0) 안에선 확신이 생길 수 없음. **확신의 해독제는 새 아이템이 아니라 싼 증거.**
- **연쇄 피벗 함정 경고**: 유통을 안 하면 0은 새 아이템으로 그대로 따라온다.
- **자산 vs 아이템 분리**: 버릴 수 없는 자산 = ① Agoda/Awin 제휴(실동작, 희소) ② 범용 모니터링 엔진(Playwright·BullMQ·동적 셀렉터). "아이템 변경"은 엔진을 버리는 게 아니라 같은 엔진 위에 더 나은 아이템을 얹는 것.

## 2. 제품 방향: "알림 도구" → "빈방·가격 레이더"

비유: **호갱노노/아실(부동산 시세 앱)** — 살 생각 없어도 시세 구경하러 들어옴. 데이터 자체가 콘텐츠.
지금은 이 데이터를 *유저 개인 알림 뒤에 숨겨놨음*. 레이더 = **누구나 보는 공개 화면으로 꺼내기.**

| 화면 | 역할 | 데이터 상태 |
|---|---|---|
| **화면 1: 개별 호텔 페이지** (`/availability/...` 살찌우기) | "지금 빈방 있음/없음 + 최근 취소표 N번 + 잔여 객실" | ✅ 즉시 가능 |
| **화면 2: 랭킹/피드** ("지금 취소표 잘 나는 숙소") | retention 엔진 (시세판) | ⚠️ 인기 호텔 자동 추적 필요 (아래 확인사항) |
| **화면 3: 여행지별 페이지** (`/destinations/...`) | SEO 유입 엔진 | ⚠️ 화면 2와 동일 |

### 레이더가 병목을 푸는 방식
| 병목 | 해결 |
|---|---|
| 안 들어온다 | "[호텔명] 빈방/취소표/가격" 검색 SEO + 구경거리 |
| 다시 올 이유 없다 | 시세판/랭킹 → 알림 없이도 수시로 구경 |
| 로그인 장벽 | 데이터는 무로그인 공개, "알림 받기"에서만 신원 확인 |

### v1은 "가격 그래프"가 아니라 "빈방 신호"로 시작 (데이터 한계 때문)
- `agoda_room_snapshots`는 **룸+요금제 단위로 수집 중**(`roomId`, `ratePlanId`, `remainingRooms`, `totalInclusive`, `raw`). 하지만:
  1. **룸 이름이 컬럼으로 안 빠져 있음** — `normalize.ts`가 룸 이름을 읽지만 opaque roomId 생성에만 쓰고 버림 (이름은 `raw` JSON에만). → 스위트/패밀리 구분 표시 불가.
  2. **룸 타입 정규화 없음** — "Deluxe Twin"/"디럭스 트윈" 등 표준 카테고리 부재.
- 따라서 **호텔 단위 최저가 그래프는 룸타입이 섞여 신뢰도 낮음** → v1 전면 배치 금지.

| 신호 | 룸타입 문제 영향 | v1 |
|---|---|---|
| 빈방/취소표 발생 | 거의 없음 (호텔 단위로도 정확) | ✅ **v1 주력** |
| 잔여 객실 / 무료취소 | 없음 | ✅ v1 |
| 가격 추이 그래프 | 큼 (오해 유발) | ⚠️ "최저가 기준" 라벨로만, 또는 보류 |

- **룸타입별 가격 추적 = v1.5 후속** (싸다): 수집은 이미 `raw`에 다 있음 → 새 스크래핑 불필요. `roomName` 컬럼 추가 + `normalize.ts` 한 줄 + 과거 `raw` 백필. 표준 카테고리 매핑은 v2.

## 3. 무로그인 이메일 알림 (올바른 첫 빌드)

핵심 멘탈 모델: **로그인을 "없애는" 게 아니라 신원을 "계정 → 이메일 + 매직링크"로 옮긴다.**

```
[지금]  검색 → OAuth 로그인 → 알림 등록     (← 여기서 대부분 튕김)
[제안]  검색 → 이메일 입력 → 확인 클릭 → 끝  (← 마찰 거의 0)
```

### 재사용 가능한 기존 인프라
| 필요 | 상태 |
|---|---|
| 서명된 토큰 이메일 액션 (수신거부) | ✅ → **매직링크에 재사용** |
| 이메일 템플릿 (ko/en HTML) | ✅ |
| IP rate limiting | ✅ → 익명 남용 방지 |
| **신규**: 익명 알림 생성 폼 + 더블 옵트인 + 매직링크 관리 페이지 | 🔨 |

### 필수 가드레일
- **더블 옵트인 필수**: "확인 메일 버튼 클릭 → 알림 시작". 안 그러면 남의 이메일 등록/스팸 가능. (기존 토큰 인프라로 구현)
- **카카오 알림은 OAuth 필요** → 이메일을 기본 채널로, 카카오는 "더 빠른 알림" 선택 업그레이드.
- **로그인은 죽이지 말고 선택으로**: 파워유저(알림 다수 관리/카톡)용. 단 **가치 획득에 절대 필수 아니게.**

## 7. 조사 결과 & 열린 확인 사항

### ✅ 조사 완료 (2026-06-05)

**① 인기 호텔 자동 추적 여부 → 안 함 (유저/관리자 등록분만)**
- `publicAvailabilitySnapshots.ts`의 공개 데이터는 `Accommodation`(등록된 숙소) 기반으로 생성됨.
- 즉 아무도 등록 안 하면 공개 콘텐츠 = 0 → **닭/달걀 문제**. 해법: 관리자가 인기 호텔을 *선제적으로 시드*해야 함 (관리자 URL/Agoda 검색 등록 기능 존재).

**② 현재 폴링은 "호텔 1개당 API 1콜" (묶기 미사용)**
- `agoda-polling.service.ts:287` → `searchAgodaAvailability({ propertyIds: [propertyId] })`. 호텔마다 따로 호출.
- `pollDueAccommodationsOnce`의 `chunkArray`는 병렬 처리용일 뿐, propertyId 묶기가 아님.
- → 대량 레이더 운영하려면 **"묶음 폴링"(100개/콜) 추가가 사실상 선행 필수.**

**③ Agoda API 제약 (developer.agoda.com 문서 확인)**
- **정확한 rate limit 숫자는 비공개** — 온보딩 때 파트너별 부여. **담당 매니저 문의 필요.** 초과 시 `429`. content/dynamic 둘 다 limiter 있음.
- 가이드: **"하루에 걸쳐 분산 호출"** (몰아 보내면 15초 차단). → 30분 사이클 안에서 폴링 분산 필요.
- **요청당 호텔 최대 100개.** 단, **묶을수록 호텔당 받는 rate 수가 줄어듦:**
  | 호텔 수/콜 | 호텔당 rate |
  |---|---|
  | 1개 | 최대 100 (룸타입 다) |
  | 2~30개 | 최대 25 |
  | 31~100개 | **1개 (최저가만)** |
- **전략적 함의 — 제약이 우리 그림과 일치:**
  - **레이더** = 100개 묶기 → 호텔당 최저가 1개 → "빈방 유무 + 최저가"엔 충분. 싸게 대량 운영. ✅
  - **개인 알림** = 호텔 1개씩 → 룸 상세 다. 초반엔 소량이라 부담 X. ✅
  - **룸타입별 가격(v1.5)** = 호텔 1개씩 호출 필요 → 인기 호텔만 선별. ⚠️
- 출처: [Demand FAQ](https://developer.agoda.com/demand/docs/faq), [JSON Search API](https://developer.agoda.com/demand/docs/json-search-api), [Getting Started](https://developer.agoda.com/demand/docs/getting-started)

**④ 우리 코드 기준 적용 여부 (중요)**
- 우리는 **구형 API-Key 방식**을 씀: `searchClient.ts:149` → `Authorization: siteid:apikey`, 엔드포인트 `affiliateapi7643.agoda.com/affiliateservice/lt_v1` (Affiliate Long Tail Search API).
- developer.agoda.com 문서는 **신형 Demand API(OAuth 2.0)** 기준 → 다른 제품. 갈라서 적용해야 함:
  - ❌ **무관**: OAuth 토큰 한도(1h 100회 / 1d 2100회), 토큰 TTL/재사용, token endpoint 분리 — 우리는 토큰 안 씀.
  - ✅ **적용**: 100개 batch + 31~100개면 rate 1개, 429 초과, 403=quota/약관 위반(무조건 retry 금지), "분산 호출".
  - ⚠️ Content Data Feed 15초 차단 = Data Feed API 쓸 때만 (우리는 search라 해당 적을 듯).
- **드러난 갭 2개**:
  1. `searchClient.ts`에 **429/retry/backoff 처리가 없음.** → 묶음 폴링 만들 때 기본 backoff 동반 필수.
  2. 담당자 문의 시 **"lt_v1 affiliate long tail search"의 한도**를 콕 집어 물을 것 (신형 Demand API와 다를 수 있음).
- **스코프 경고**: Redis 분산 rate limiter·엔드포인트별 버킷 6개 등은 트래픽 많은 서비스용 과설계. 유저 0인 지금 범위는 **묶음 폴링 + 기본 backoff + 보수적 호출 속도(낮은 concurrency·약간의 delay)까지**. 분산 버킷은 유저 생긴 뒤.

### ⬜ 남은 확인 사항

- [ ] **Agoda 담당 매니저에게 정확한 rate limit 숫자 문의** (천장 확인 → 시드 호텔×날짜 규모 역산) — *최우선, 본인만 가능*
- [ ] 각 타깃 커뮤니티의 외부 링크/홍보 정책
- [ ] 이메일 발송 도달률/스팸 점수 (무로그인 대량 발송 대비)

### 도출된 엔지니어링 액션 (레이더 선행 작업)

1. **묶음 폴링 추가** — 같은 날짜·인원 시드 호텔을 100개씩 1콜로 (최저가만 수신). 클라이언트는 이미 100개 지원, 폴링 쪽 연결만.
2. **기본 backoff 동반** — `searchClient.ts`에 429/5xx 재시도(exponential + Retry-After 존중), 403은 retry 금지·body 로깅. *분산 버킷은 과설계, 지금은 제외.*
3. **폴링 분산** — 30분 사이클 내 호출을 시간축에 흩뿌려 429/차단 방지. 낮은 concurrency + 호출 간 약간의 delay.
4. **인기 호텔 시드** — "잘 매진되는 호텔 × 성수기/연휴/주말 날짜" 50~100개부터.
